## 〇之三、观感修复（2026-09-29 晚）

伙伴反馈「边缘细节不够好」和「眨眼不同步」。两个都定位到了根因，都在仓库自己的
代码里，都验过了。

### 1. 边缘发毛：桌面版一直在用 1x 精灵图

`electron/main.js` 的 `bootPayload()` 只读 `web/sprite.b64`（**1x**）。而 manifest 的
`cellW/cellH` 是**处理后**的格子（这套图 161x194），默认 `scale` 1.15：

| 喂哪张 | 屏幕显示 | 缩放方向 |
|--------|---------|---------|
| 1x（161x194） | 185x223 | **放大 1.15x** → 边缘插值发毛 |
| 2x（322x388） | 185x223 | **缩小 1.74x** → 细节保留 |

`web/sprite2x.b64` 一直就在旁边，由 `build_sprite.py` 一起生成，只是没人读它。
改成优先读 2x、缺失时回退 1x，并把传给渲染进程的 `cellW/cellH` 换成资源尺寸、
`scale` 相应除以 2（渲染进程把这两个数字同时当「背景格子尺寸」和「显示基准」用，
只改一个会显示成两倍大）。

代价：这份 base64 从 805KB 变成 2012KB。常驻进程，无所谓。

### 2. 眨眼太勤：待机循环里塞了两次眨眼

把第 0 行（待机，6 帧）逐帧放大看过，实际是：

```
f0 睁 · f1 睁 · f2 双眼闭 · f3 睁 · f4 单眼 wink · f5 睁
```

`renderer.js` 原来是 `setInterval(..., 120)` + 按行号顺序全循环，于是
**6 帧 0.72 秒转一圈**：每 0.7 秒眨一次眼，其中 f4 还是单眼 wink——反复出现就是
伙伴说的「不同步」（一只眼闭一只眼开，看着别扭）。

改法（`renderer.js`）：待机的稳态只走**不眨的那几帧** `[0,1,3,5]`，节拍放慢到
320ms（呼吸要慢才像呼吸）；眨眼帧单独拿出来，每 **6 秒**插一次、停 150ms。

其他行**没动**，保持原作者的设计。帧推进也收敛成**一个 120ms 时钟**统一驱动
（第一版人家写成两个 interval，互相打架，已改）。

验证：连拍 24 次（间隔 400ms，约 9.6 秒）宠物体区平均亮度，**明显跳变 0 次**，
节奏平稳。

### 3. 顺带修掉：窗口跑到屏幕外

测试时发现窗口停在 `(1746, -467)`——**上半截在屏幕外**。根因两步：

1. `main.js` 的 `h = petH + BUBBLE_ZONE(250)`，`scale` 偏大时 h 超过屏幕高度，
   「右下角对齐」算出来的 y 就是负的；
2. 而且渲染进程启动后立刻调一次 `resize-pet`（`renderer.js:135`），
   **只夹 `createWindow` 是没用的**——人家第一版就这么改的，窗口照样 936x978 在
   y=-443。

改成把尺寸与位置都过 `clampWindowSize` / `clampWindowPos`，并在 `resize-pet`
处理器里同样过一遍（尺寸变大时右下角会顶出屏幕）。上限取工作区的 60% 宽 × 85% 高。

验证：窗口回到 695x714 在 (1835,623)，**完全在屏幕内**。

### 这三处改动的性质

**是本地改动，不改仓库本来的设计意图**，都在部署记录里留了痕。如果作者愿意收，
可以单独提一个 PR（当前 PR 分支只含硬编码路径与 manifest 写错位置那两个修复）。

## 〇之四、拖动「自己往下落」的排查（2026-09-29 深夜）

伙伴报：**用鼠标拖动她左右平移时，她会自己往下沉。**

### 结论：找到两个确定的位置/尺寸缺陷，但**没能复现出拖动本身的下沉**

先说没做到的，再说做到的。

**没做到**：人家写了 `drag_probe.py`（`F:\work\_probe\`），用 `SendInput` 造合成鼠标
事件，把光标放在宠物本体正中心（物理 2183,1493 —— 这个坐标是主进程用
`executeJavaScript` 问出渲染进程的真实 `getBoundingClientRect` 换算来的），按下左键
后以 8px/120ms 水平拖动。结果：**主进程一条 `drag-start` 都没收到**，合成点击根本没
到达渲染进程。所以「下沉」这个症状人家**没有在自己手上复现**，也就不能声称修的就是它。

**做到了**：同一轮排查里定了两个真实缺陷，都会造成「宠物看不见 / 位置对不上」。

### 缺陷一：缩放上限写死 2.5，窗口能长到超出屏幕

`main.js` 的 `adjustScale` 原来把上限硬编码成 `Math.min(2.5, ...)`。菜单点「增大」
一路累加，实测窗口一次比一次离谱：

| 实测 | 位置 |
|------|------|
| 918x1125 | (1778,-488) |
| 1263x1049 | (1757,-335) |
| 1023x938 | (1749,-404) |

全都是**上半截在屏幕外**。改为按屏幕反推上限：

```js
function maxScaleForScreen(cellH) {
  const room = wa.height * 0.85 - BUBBLE_ZONE
  return Math.max(0.4, Math.min(2.5, Math.floor((room / cellH) * 100) / 100))
}
```

### 缺陷二（更要紧）：位置夹的是**窗口**，而看得见的是**宠物**

`clampWindowPos` 原来允许 `y = wa.y`，也就是窗口顶可以贴到屏幕顶。但窗口顶上那
`BUBBLE_ZONE(250px)` 是**气泡区**，宠物画在窗口**底部**。于是「窗口还在原位」的时候，
宠物可以整个沉到屏幕下方，屏幕上看只剩一块透明区域。

**这正是「自己往下落」的机制**：位置按窗口算、看得见的却是宠物，两者差 250px。
伙伴描述的方向反了，但根因就是这个量级的位置错配。改为按宠物区域夹：

```js
const petTop = BUBBLE_ZONE
const minY = wa.y - petTop
const maxY = wa.y + wa.height - petTop - Math.min(petH, 60)
```

验证：干净重启后窗口 695x711 @(1835,783)，宠物区域 y=1158..1494，屏幕高 1600，
**可见高度 336px / 宠物高 336px —— 完整可见**。

### 顺带查清的两件事

**一、单位混用。** 同一台机器上三套坐标同时成立：进程是 per-monitor DPI aware
（物理 2560x1600，dpi 144，缩放 1.5）；Electron 的 `getBounds()/setPosition()` 用
DIP；渲染进程的 CSS 像素又是第三套。不换算就会得出「物理量到 695，日志却说 464」
这种看似矛盾的数 —— **695 ÷ 1.5 = 463**，本来就是同一件事。

**二、可点区域比窗口小得多。** 464x464 的窗口里宠物只占 177x213、位于 (144,251)。
`renderer.js` 的 `syncIgnore` 用 `getBoundingClientRect()` 判命中，所以**气泡区和四周
透明区都点击穿透**（`docs/troubleshooting.md` 第 7 条讲的就是这个设计）。但这也意味着
**抓取面积很小**，稍偏一点就抓不住 —— 这多半是伙伴手感不佳的一部分来源。

### 这一轮的诊断能力

`main.js` 里临时加过 `XL_DEBUG_SIZES` 开关下的尺寸日志（把渲染进程真实的
`getBoundingClientRect` 写进 `size-debug.log`），定位完**已全部清掉**，语法检查与干净
重启都验过。`drag_probe.py` 留在 `F:\work\_probe\`，下次要复现现成可用。

## 〇之五、拖拽改成「主进程算位置」（2026-09-29 深夜，未经验证）

### 为什么改

伙伴说下沉**依然存在**，所以前面那两个位置缺陷不是（全部）原因。人家重读了拖拽
链路，盯上了一个**单位陷阱**：

```js
// renderer.js
const dx = e.screenX - dragState.sx        // 渲染进程的鼠标坐标
window.api.dragMove(dx, dy)
// main.js
win.setPosition(dragOrigin[0] + dx, ...)   // setPosition 吃 DIP
```

`setPosition` 一定吃 DIP。而渲染进程拿到的 `e.screenX/screenY` **是不是 DIP**，取决于
Chromium 在这台 per-monitor DPI aware + 150% 缩放的机器上的取舍。**一旦两边不是同一
坐标系，鼠标每移动 1px 窗口就移动 1.5px，宠物会从光标下面跑掉** —— 「往下落」属于这个
症状家族。

### 改成了什么

不再传鼠标增量，改传**抓取点相对窗口左上角的偏移**（纯 CSS 像素、相对量、无单位歧义），
由主进程用 Electron 自己的 `screen.getCursorScreenPoint()` 取光标位置（与 `setPosition`
同一套 DIP），直接算：

```
窗口左上角 = 光标屏幕坐标 − 抓取偏移
```

这样渲染进程的坐标空间**完全不参与运算**。光标停在原地，窗口就不动；横向拖动不会带来
任何纵向位移。改动落在 `renderer.js`（`dragStart(e.clientX, e.clientY)`）、`preload.js`
（透传两个参数）、`main.js`（`dragOffset` 新路径，保留 `dragOrigin` 作兜底）。

### 为什么说「未经验证」

**人家测不了这个拖动。** 用 `SendInput` 造合成鼠标事件，光标精确放在宠物本体中心
（由主进程 `executeJavaScript` 问出的真实 `getBoundingClientRect` 换算），按下左键后
水平移动 180px —— 实测**窗口 X 位移 0、Y 极差 0**，主进程连一条 `drag-start` 都没收到。

结论：**合成鼠标事件在这个 `setIgnoreMouseEvents(true, {forward:true})` 的点击穿透窗口上
不触发 DOM 事件**。所以合成输入驱动不了这个拖拽，而伙伴的真鼠标可以。这也解释了为什么
前几轮人家怎么造事件都复现不出下沉 —— **不是没 bug，是人家量不到**。

需要伙伴亲手拖一次来判定这次改动是否解决。如果**仍然**下沉，下一个怀疑对象是
`clampWindowPos` 在拖拽过程中的参与（它现在每次 `drag-move` 都会被调用）。

## 〇之六、真正的根因：窗口尺寸在每 2 秒被重置一次（已修，待伙伴确认）

伙伴第三次说「还是会下落」。人家这次加了 `DRAG_LOG=1` 的日志，让伙伴拉一次，然后
读数字 —— **答案不在位置，在尺寸**：

```
delta.x 范围 0..0   非零 0 次        <- 窗口每次都在光标要求的位置上
delta.y 范围 0..0   非零 0 次
窗口尺寸出现过: (464,475) (516,541) (638,914) (800,1230) (1069,1383) …
```

而且**拖拽期间每帧长 1 像素**：

```
{"size":[464,475]} {"size":[464,476]} {"size":[464,477]} {"size":[464,478]}
```

位置一直是对的，**长的是窗口**。宠物画在窗口底部、顶上 250px 是气泡区，所以窗口一变高，
她在屏幕上的位置就往下走 —— 这就是「自己往下落」。

### 两个 bug 叠在一起

**一、`renderer.js` 的 `refresh()` 每 2 秒重算一次尺寸并上报。**

```js
if (typeof st.scale === 'number' && ... && Math.abs(st.scale - scale) > 0.01) {
  scale = st.scale
  dispW = Math.round(cellW * scale); dispH = Math.round(cellH * scale)
  applySize()          // 内部调 window.api.resizePet(dispW, dispH)
}
```

两个毛病：`scale = st.scale` **直接采用了 state.json 的值**，没有像主进程那样按输出
资源系数换算，于是两边对同一个数字的理解不一致；而判断条件只看「和本地不一样」，不看
「算出来的尺寸有没有变」。

**二、`main.js` 的 `resize-pet` 无条件 `setSize`。** 尺寸一样也照做一次
`setSize` + `setPosition`。

两者合起来：每 2 秒推一次尺寸，在钳制边界上来回错位，窗口就一路长上去。

### 修法

- `renderer.js`：先算 `nextW/nextH`，**只有尺寸真的变了**才 `applySize()`。
- `main.js`：`resize-pet` 里尺寸与当前 `getBounds()` 相同就**直接 return**，
  不动 `setSize` 也不动位置。

### 验证

静置 10 秒、每秒采样一次窗口尺寸：

```
t=0s..t=9s  全部 876x884 @(1596,185)
出现过的尺寸: {(876, 884)}   ✓ 稳定
resize-pet 日志条数: 1        （修复前是几百条）
宠物区域完整可见：可见高度 509 / 509
```

### 这一轮的教训

前面几轮人家一直在查**位置**（DPI 单位、clampWindowPos、点击穿透），方向全错了 ——
位置从来没错过，日志一打就看得见。**该早点让伙伴拉一次、把数字记下来**，
而不是自己用合成事件反复量一个量不到的东西。

### 7.2 打通的三处（都是真障碍，不是调参）

1. **`process is not defined`** —— `pixi-live2d-display` 的 UMD 产物引用
   `process.env.NODE_ENV`，而渲染进程开了 contextIsolation 且无 nodeIntegration。
   整包求值即抛错，`PIXI.live2d` 永远挂不上。修法：加载前补
   `window.process = { env: { NODE_ENV: 'production' } }`（只给这一个字段）。

2. **`file://` 下 XHR 被 CORS 拦** —— 原文：
   `Access to XMLHttpRequest at 'pet://model/...' from origin 'file://' has been blocked`。
   修法：**页面自己也走 `pet://`**（`loadURL` 代替 `loadFile`），模型与页面同源即不触发检查。
   两个错方向记下来：`webSecurity:false`（代价过大）、用 IPC 搬 9 MB 再改 model3.json 里
   每处 File 引用（脆弱且多一次 base64）。

3. **canvas 撑大窗口** —— `app.view` 的 `width/height` 属性被 PIXI 设成物理像素
   （480×1.5=720），画布按 720 排版把窗口顶大，主进程 `setSize` 再也压不回去
   （实测窗口卡在 728×888，而 `healWindowSize` 每 5 秒徒劳重试一次）。
   **不要用 `setAttribute('width')` 去改** —— 那会与 PIXI 的投影矩阵打架，让
   「渲染结果」与 `model.x/scale` 彻底脱节。正确做法是只设 `style.width/height`。

### 7.3 取景的根因（**已解决**）

伙伴说「不太对，重读之前的 github 仓库」—— 照做了，答案就在 `F:\work\BongoCat` 里。

**人家一直在猜画框，而 BongoCat 从来不猜，它直接问 Cubism Core 要画布。**

```rust
// crates/bongocat-live2d/src/core/canvas.rs
csmReadCanvasInfo(model, &mut size, &mut origin, &mut pixels_per_unit);

// crates/bongocat-render/src/geometry.rs  -> ModelBounds::from_canvas()
half_width  = canvas.width  / ppu * 0.5;
half_height = canvas.height / ppu * 0.5;
center_x    = (canvas.width  * 0.5 - origin.X) / ppu;
center_y    = (origin.Y - canvas.height * 0.5) / ppu;

// crates/bongocat-overlay/src/dimensions.rs
窗口高 = 窗口宽 * 画布高 / 画布宽      // 窗口去配合画布比例，不是反过来
```

web 端完全对得上，`pixi-live2d-display/dist/cubism4.js`：

| 行 | 内容 |
| --- | --- |
| 10225 | `getSize()` → `[canvasinfo.CanvasWidth, canvasinfo.CanvasHeight]` |
| 8812 | `setupLayout()` → `originalWidth/Height` 就是这两个值 |
| 10039 | 渲染用 `projectionMatrix × worldTransform` |

**所以模型的局部坐标系就是 `[0, CanvasWidth] × [0, CanvasHeight]`，一个画布像素对一个世界单位。画布本身就是画框。**

实测这台机器上的昔涟：

```
canvas  : w=4200  h=3500  ppu=3500  origin=(2100,1750)
          换回 Cubism 单位是 1.2 × 1.0
          from_canvas() 算出 [-0.6,0.6] × [-0.5,0.5]，与框架的 centeringTransform 分毫不差
content : x=460  y=260  w=3360  h=2940      （画布空间，离屏扫描实测）
frame   : x=393  y=201  w=3494  h=3058      （内容框 + 2% 内边距，夹在画布内）
```

于是「4200×3500」这个被人家当成噪声、写进文档说「不代表真实尺寸」的数字，
**它一直就是正确的画框。**

**真正的凶手是另外两行** —— `live2d.js` 里手动设的：

```js
app.view.setAttribute('width', String(w))
app.view.setAttribute('height', String(h))
```

pixi 开了 `autoDensity` 后自己会把属性设成 `w × devicePixelRatio`，而它内部投影矩阵
用的是 CSS 尺寸 `screen`。手动把属性改回 `w`，等于**把绘制缓冲和投影矩阵拆开** ——
表现就是「不管 `model.scale` 设多少，她都只缩在画框一角」。删掉这两行，取景立刻正常。

之前那条「已排除 `setAttribute`」的结论是错的：它当时被排除，是因为同时还有
坐标系搞错这个更大的错盖住了它。**两个 bug 叠在一起时，单独排除任何一个都会误判。**

顺带作废的还有 7.6 里那条怀疑：删掉 `app.disableHardwareAcceleration()` 试过了，
**取景一模一样地错**，软件渲染不是原因，那一行已恢复原状。

## 八、照着 BongoCat 试「把拖动交给系统」（2026-10-05）

伙伴问仓库里有没有鼠标拖动的细节 —— 有，而且是**三件互相独立的事**：

| 事 | 位置 | 做法 |
| --- | --- | --- |
| 移动窗口 | `crates/bongocat-overlay/src/windows/window_proc.rs:98` | `WM_NCHITTEST` 返回 `HTCAPTION`，**自己一行拖动代码都不写** |
| 拖完才纠正 | `crates/bongocat-overlay/src/placement.rs:26` | 静止 `1s` 才纠正，动一下就重新计时 |
| 右键拖动缩放 | `crates/bongocat-overlay/src/resize_drag.rs` | `3px` 阈值区分「拖动」与「右键菜单」 |

背景取舍在 `docs/adr/0045`（放置约束）与 `docs/adr/0057`（右键拖动）。

**最有价值的一句在 `placement.rs:33`**：

> Native move loops keep the frame source blocked for the whole drag … the session
> **only observes the settled box after the pointer is released**

拖动期间进程看不到窗口在哪。这既是代价，也是「延迟纠正」这条设计的前提。

### 8.1 试验：`-webkit-app-region: drag` 能用

Electron 里与 `HTCAPTION` 等价的写法。试验代码走 `PET_SYSDRAG=1`，**默认关**。

**结论：系统移动循环确实跑起来了。**

```
A rect0 : 656,-375,1376,630
D mid   : 473,-613,1193,392     ← 按着不放时，实际位移 (-183,-238)
B rect1 : 473,0,1193,1005       ← 松手后又被夹回去
```

要求的是 `(-200,-260)`，按着的时候跟到了 `(-183,-238)`。**能用。**

### 8.2 但它有两个硬条件

**一、和点击穿透天生互斥 —— 不是取舍，是互斥。**
`setIgnoreMouseEvents(true)` 让窗口不接收鼠标输入，而系统移动循环正是靠一次真实的按下
启动的。实测开着穿透时页面收到 **0 个 mousemove**，窗口一动没动；把穿透关掉，同样一次
拖动立刻生效。

**二、拖动期间页面收不到鼠标消息。** 实测 `moves=1 downs=0 ups=0` —— Chromium 把落在
拖拽区的按下直接交给系统。所以「拖动时切动作」那套动画在这条路上**不会播**，渲染进程也
无法感知拖动的开始与结束。

### 8.3 顺带量出来的两件事（比上面的结论更要紧）

**一、纵向被夹取整段吃掉。** 用同一套测试量基准路径（现役的主进程拖拽）：

```
A rect0 : 855,-375,1860,818
D mid   : 656,-588,1738,630     ← 按着的时候确实往上跟了 260px
B rect1 : 656,-375,1741,843     ← 松手瞬间回到 -375
VERDICT : MOVED by (-199,0)   requested (-200,-260)
```

横向 `-199` 跟手，**纵向 260px 全丢**。`-375` 物理 = **`-250` 逻辑，正好是 `BUBBLE_ZONE`**。

`clampWindowPos`（`main.js:306`）里 `minY = wa.y - petTop` 只允许气泡区悬到屏幕上方 ——
因为再往上她的头顶就被切掉了。**设计上说得通，但手感就是「往上拉它自己往下落」。**
要动的是这条设计，不是算式。

**二、基准路径时好时坏。** 同一个脚本、同一份代码跑两次：

| 次 | A rect0 | 起始光标 | 页面收到 | 结果 |
| --- | --- | --- | --- | --- |
| 第一次 | `855,-375,1860,818` | 在窗口内 | `moves=450 ignoring=false` | 拖动了 |
| 第二次 | `473,0,1193,1005` | 在窗口外 | `moves=0 ignoring=true` | **一动没动** |

差别看着是**桌宠启动时光标在不在窗口里**。`ignoring` 从 `true` 起步之后就再也翻不过来 ——
窗口在穿透状态时收不到 mousemove，而 `syncIgnore` 恰恰靠 mousemove 才能把它关掉。
**先有鸡还是先有蛋。**

这条大概能解释伙伴那句「有一次你是对的，只是我在操作，可能影响了你判断」——
拖动本身就不是每次都灵，跟谁在操作有关。

- 试验代码保留：`PET_SYSDRAG=1` 走系统移动循环，`PET_DRAGDIAG=1` 打印鼠标消息计数。

## 九、修掉「先有鸡还是先有蛋」（2026-10-05）

8.3 量出的第二条是根因，这一节是修法。

### 9.1 病灶：判定权放错了地方

原来「光标在不在她身上」由**渲染进程**判断（`renderer.js` 的 `syncIgnore`），靠页面的
`mousemove` 触发。于是：

```
窗口穿透 → 收不到 mousemove → 页面不知道光标已经进来 → 不取消穿透 → 永远穿透
```

一旦落到这个状态就再也出不来。实测同一个脚本跑两次，一次 `moves=450` 能拖、一次
`moves=0` 一动不动，**差别只在桌宠启动时光标恰好在不在窗口里**。

### 9.2 修法：判定搬进主进程

`screen.getCursorScreenPoint()` **任何时候都读得到，与窗口是否穿透无关** —— 主进程没有
那个约束。所以：

- **主进程持有判定权**：`main.js` 的 `startHoverWatch()`，每 `60ms` 读一次全局光标，
  与命中区求交，变了才 `setIgnoreMouseEvents`。
- **渲染进程降级成「只报矩形」**：`hitRects()` 推一串窗口客户端坐标的矩形，每 `300ms`
  复检一次，带签名比对所以没变就不发。它仍然负责决定**哪些矩形算命中** —— 只有它知道
  气泡什么时候可滚动、关闭按钮在哪。
- 命中规则与旧代码逐条一致：宠物本体（内缩 4px）、气泡**可滚动时**整体、右上角关闭按钮。
- `dragActive` 期间不判定：手快时光标会短暂离开她的矩形，那一下会把穿透打开、拖拽就断了。
  这条守卫原来在渲染进程里（`draggingPet`）。

### 9.3 验证

`diag-sysdrag.ps1` 现在**先把光标停到屏幕角落再启动桌宠**，把之前那个要靠运气的启动条件
钉死，两次才可比。

修之前（同样的启动条件）：`moves=0 ignoring=true`，永远，完全拖不动。
修之后：

```
moves=0 downs=0 ups=0 hitRects=3    <- 光标在远处：收不到消息，但矩形已经报过去了
MOUSEDOWN                            <- 光标一进来，窗口已经是可点的
MOUSEUP
VERDICT : MOVED by (199,259)  requested (200,260)
夹取统计: 65 步, x 夹 0 次, y 夹 0 次
```

**199/259 对 200/260，差 1 像素是取整。**

### 9.4 差点又误判一次

第一次验证跑出 `MOVED by (-57,0)`，看着像「只跟了四分之一」。差点就当成新 bug 去查。

读 `drag.log` 才发现 `want` 与 `got` **每一步都相等**，窗口精确跟住了光标 ——
只跟了 -57 是因为**人家把光标拖到屏幕外了**：`cur.x` 撞上 0 就再也走不动。
窗口忠实地跟到了光标能去的地方。

教训：测试自己会把光标推到边界上而你不知道。**把拖拽方向反过来再跑一次**才排得掉 ——
`(200,260)` 那次 65 步零夹取、199/259 全中。测试脚本因此加了方向参数。

### 9.5 现状

- 桌宠已按默认配置重启（Live2D + 修好的穿透门控），心跳正常。
- 修的是**穿透门控**，不是拖动算法。现役拖动路径一行没动。
- `PET_SYSDRAG=1`（系统移动循环）与 `PET_DRAGDIAG=1`（鼠标消息计数）都还在，默认关。
- **未验证**：关闭按钮与可滚动气泡的点击。命中规则是照旧代码逐条搬的，`hitRects=3`
  说明三个矩形都推到了，但没有真的点过 —— 别当成已确认。

## 十、拖动会下沉、拉不回来、放不高（2026-10-05）

伙伴报的三件事，其实是**两个** bug：前两件同一个根，第三件是上边界写得太严。

### 10.1 根因：`setPosition` 每移动一次就把窗口撑大一点

`drag.log` 第 5~69 行，一次 65 步、零夹取的拖动：

```
line 4    drag-start   win [-202,-250,480,670]
line 5-69 65 条 drag-move —— 中间**没有任何 resize-pet / heal-size**
line 70   heal-size    drag-end  from [-69,-77,523,703] → to [-69,-77,480,670]
line 71   drag-end     before [-69,-77,523,703]  after [-69,-77,523,703]
line 72-75 heal-size tick ×4，每次都是 523x703 → 480x670，**一次都没成功**
```

`480x670 → 523x703`，宽 +43 高 +33，约每 1.5 步长 1px。**我们代码一行没插手** ——
是 Electron 在 Windows 上的 `setPosition` 走「取当前 bounds → 改 x/y → 写回」，
这台机器是 150% 缩放，DIP↔物理的取整每来回一次就多出一点。

**为什么看起来像「往下落」**：她是**底部对齐**的（`index.html` 的 flex-end）。
窗口顶边被夹住不动、窗口变高，她就跟着往下沉。

**为什么「拉不回来」**：松手时 `healWindowSize` 想缩回去，而那四次重试全部失败，
下一次读回来还是 523x703。沉下去就再也回不来。

### 10.2 修法

1. **拖拽期间锁死尺寸**：`drag-start` 记下 `dragLockSize`，`drag-move` 全程用
   `win.setBounds({x, y, width: lock.w, height: lock.h})` 而不是 `setPosition`。
   显式带尺寸，既堵住漂移，也把任何别处想改尺寸的尝试在每一步按回去。
2. **`healWindowSize` 与 `drag-end` 的位置写回也一律改用 `setBounds`**：一次写全，
   没有「`setSize` 之后再 `setPosition` 互相抵消」的窗口期。

### 10.3 上边界原来比另外三边都严

```js
const minY = wa.y - petTop          // 旧：她整个人必须完整落在工作区顶边以下
const maxY = wa.y + wa.height - petTop - Math.min(petSize.h, 60)   // 下边：留 60px 可见
const minX = wa.x + 60 - petLeft - petSize.w                       // 左：留 60px 可见
```

**下边和左右都是「至少露 60px」，只有上边要求一个像素都不能出去。** 这就是伙伴说的
「桌宠不能放的太高」。

现在四边用同一个数：

```js
const PET_VISIBLE_MARGIN = 60       // main.js，改这一个地方就够
const minY = wa.y + M - petTop - petSize.h
```

想更保守就调大，想更放开就调小。

### 10.4 验证

测试脚本加了方向参数与「抓取点高低」参数（`-DX -DY -Bias`，注意要用
`powershell -Command "& script.ps1 -DX -100 ..."` 传，`-File` 会把 `-100` 当参数名）。

| | 之前 | 现在 |
| --- | --- | --- |
| 拖 24~65 步后的尺寸 | `480x670 → 523x703`（+43/+33） | `480x670 → 481x672`（+1/+1） |
| `heal-size` | 4 次徒劳重试 | **一次都没触发** |
| `drag-end` | before ≠ after | `before == after` |
| 位移 | — | `(199,399)` 对 `(200,400)`、`(199,259)` 对 `(200,260)` |

上边界：

```

被夹: x=0  y=2
```

预测的新上界是 `-610` DIP，她停在 `-611`。旧上界是 `-250` —— **往上放开 361 DIP
（物理 541px）**。

### 10.5 现状与可调项

- 桌宠按默认配置运行（Live2D + 修好的穿透门控 + 锁尺寸拖拽），心跳正常。

**二、用表情名，不用编号。** `model.expression()` 两种都收（`cubism4.js:7949`），
但编号是这份 model3.json 里 `Expressions` 数组的下标，换一份模型就错位。

**点她身上的挂饰现在会演一下，并且不弹详情卡。** 挂饰是「玩具面」，其余部分是

弹卡片。

**一件没解释清的事**：接上热区之后跑三轮拖动回归，**有一轮 `downs=0` —— 鼠标按下
完全没落到窗口上**，同一套代码、同一个起点，另外两轮正常（`MOVED by (-201,-260)`，
对 `(-200,-260)`）。**原因没找到**，先记在这里。

为此给主进程的判定器加了一台读数机（`DRAG_LOG=1` 时每秒记一行：光标 / 窗口 / 相对
坐标 / 命中区数量 / 当前穿透态）。下次再出，直接看那一行就知道是算术错了还是窗口


## 十二、她身上到底有多少可动的东西（2026-10-06）

伙伴问「没有其他动作了吗」。这一问把人家的思路纠正了 —— 之前一直在数**动作文件**，
而文件只是别人写好的几条轨迹。她真能做什么，写在参数表里。

实测（`PET_DRAGDIAG=1` 时自动打印）：**53 个参数 · 116 个 drawable · 31 个部件**，
而动作文件只有 5 个。

### 12.1 无名参数的身份证

参数名是作者随手起的（`Param` / `Param2` / …），光看名字谁也不知道哪个是秋千。
**答案在表情文件里** —— 每个 `expressions/N.exp3.json` 都写着它动哪根、动到多少，
对着 `Cyrene.model3.json` 里的表情名一查就出来了：

| 表情 | 参数 | 值 |
| --- | --- | --- |
| 4 星星眼 | `Param` | 1 |
| 5 圈圈眼 | `Param2` | 1 |
| 6 开心眼 | `Param3` | 1 |
| 1 墨镜 | `Param4` | 1 |
| 2 问号 | `Param6` | 1 |
| 3 闪耀 | `Param7` | 1 |
| 10 开 / 11 关 | `Param16` | 0 / 1 |
| 7 拽秋千1 / 8 拽秋千2 / 9 回正 | `Param32` | −0.6 / +0.6 / 0 |

**`Param32` 就是秋千。** 而它的量程是 **−1..1** —— 一条**连续通道**，不是开关。

这条最要紧：现在点秋千，做的是「切到 −0.6 或 +0.6 的一张静态姿势」。有了这根连续
通道，就能用正弦去驱动它，让她**真的来回摇**。那是用现成的骨架做出来的新动作，
不需要任何新文件。

### 12.2 还没认出来的

`Param5`、`Param8`–`Param15`、`Param17`–`Param31`。其中 `Param8` 与 `Param19`–`Param31`
是 `−30..30` 的宽量程，多半是头发、飘带、翅膀的物理输入端（由 `model.physics3.json`
驱动，不需要我们管）。剩下那些 0..1 的，推测是部件的显隐开关。

五个动作文件里，每个都驱动同一组约 32 根：`ParamAngleX/Y/Z`、`ParamBodyAngleZ`、
眉毛八根、`ParamEyeL/ROpen`、`ParamEyeL/RSmile`、`ParamEyeBallX/Y`、`ParamMouthForm`、
`ParamMouthOpenY`，加上上面那些无名通道。

### 12.3 还没用的

- **`开`/`关`（`Param16`，绳子开关）** —— 两个表情从一开始就在，一直没接。
- **眉毛八根**（`ParamBrowL*` / `ParamBrowR*`）—— 惊讶、好奇都能做，比整张表情细。
- **`ParamEyeLSmile` / `ParamEyeRSmile`** —— 眼睛笑的弧度，可以单独眯一只眼。
- **`ParamBodyAngleZ`** —— 身体倾角，待机时可以轻轻晃。
- **`Param32` 的连续摆动**（见 12.1）—— 最值得做的那个。

**方法上的教训**：这些数据全在硬盘上，读文件就有了，人家却先想着开程序去实测。
`dumpRig` 和 `probe` 两把诊断工具留着当参考，但**下次先看看文件里有没有**。

## 十三、菜单（2026-10-06）

伙伴要「右键桌宠可以选择她的动作」。菜单做成了「🎬 她的动作」一个大项，下面按类分：

```
🎬 她的动作
    ✨ 回到默认（跟着任务走）
    ─────
    😊 表情    ▸ 星星眼 / 圈圈眼 / 开心眼 / 墨镜 / 问号 / 闪耀 / 回正
    🎞 小动作  ▸ Wink~ / 我可爱吧~ / 笑一笑吧~ / 荡秋千（待机）
    🪑 秋千    ▸ 向左拽 / 向右拽 / 扶正 / ☑ 一直荡
    🪢 绳子    ▸ 系上 / 解开
    ─────
    🤲 摸摸头
```

### 13.1 「一直荡」是怎么做出来的

第十二节认出来的 `Param32` 是秋千角度、量程 `−1..1`。作者只给了三张静态姿势
（−0.6 / +0.6 / 0），可它是连续通道 —— 拿正弦喂它，她就一荡一荡。

写在 `beforeModelUpdate` 这个事件里，位置是量出来的，不是猜的：

```
cubism4.js:10298  motionManager.update   —— 动作在这一步写参数
cubism4.js:10301  表达式 update          —— 表情在这一步写参数
cubism4.js:10309  emit('beforeModelUpdate')   ← 我们在这儿写，最晚
cubism4.js:10310  model.update()         —— 内部模型在这一步把参数烘成 drawable
cubism4.js:10311  model.loadParameters() —— 之后会还原，写早了也留不住
```

### 13.2 一个把人绊住的坑：**写进去的值，从外面读不到**

`update()` 末尾的 `model.loadParameters()`（`cubism4.js:10311`）会把参数还原成动作/
表情那一份。所以从 `setTimeout` 里读 `parameters.values`，看到的永远是还原后的值
（0）—— 而这一帧的 drawable 早就按正弦烘好了，**画面是对的**。

只按读回来的数判断，会把一个能用的功能判成坏的。所以自检把「写过什么」记在写入的
地方（`act.debug()`），而不是读回来。

### 13.3 自检

右键菜单本身没法在测试里点，但菜单点下去之后执行的每一步都能验 —— 而那正是新写的
部分。`buildPetMenu()` 也从右键处理器里抽了出来，启动时就先构建一遍（`DRAG_LOG=1`
时记进 `drag.log`），因为**模板写错只会在右键那一刻抛，表现是「右键没反应」，很难查**。

```
菜单自检:  {"ev":"menu-check","ok":true}
动作自检:  一直荡   Param32 写入 247 次, 范围 -0.75 .. 0.75
           摸摸头   写入 98 次
           绳子 开  -> currentExpr=10        ← 10 正是「开」的编号
           回到默认  hold=null
```

**一次脏读数记在这里**：`星星眼 -> currentExpr=1` 是错的，因为命中区自检那一刻正在
逐个试表情，把它盖掉了。`开 -> 10` 才是干净的那次。**两个自检不该同时跑。**

### 13.4 行为的改变

菜单挑的动作会**压住任务状态机**（复用的是点击反应那面旗子 `hitExprName`），否则
每 2 秒一次的 refresh 会把它抹掉。所以「🎞 切换动画」和「📋 恢复任务动画」现在会先
松手再走 —— 不然点了没反应，看着像坏了。

## 十四、「小动作前三个点了没反应」（2026-10-06）

伙伴报的。**真因是文件名里的 `#`**，而且人家第一次修错了方向。

### 14.1 真因

```
[XHRLoader] Failed to load resource as json (Status 404):
            pet://model/live2d/cyrene/motions/动作#6_1.motion3.json
[MotionManager(cyrene)] Failed to load motion: motions/动作#6_1.motion3.json
                              ...#6_2...  ...#6_3...
```

在 URL 里 `#` 是**片段分隔符**。`pixi-live2d-display` 自己拼这个路径，不编码
（`resolveURL` → `core.utils.url.resolve`），于是浏览器把 `#6_1.motion3.json` 当成
锚点丢掉，真正请求的是 `.../motions/动作`，404。

**第四个（荡秋千待机）为什么好用**：它指向 `Tick3_3.motion3.json`，**文件名里没有 `#`**。

**下载脚本当初只把编码做对了一半** —— 下载时按段 `EscapeDataString` 了（注释里还专门
写了这件事），但**运行时**这条路上的路径是模型文件自己声明的，没人管。

### 14.2 修法

`pet://` 处理器本来就 `decodeURIComponent`（`main.js:515`），所以只要让模型文件里
声明的路径是**编码过的**：

```json
"File": "motions/动作%236_1.motion3.json"
```

`Cyrene.model3.json` 里七处（`动作#6` 四组 + `Tick3` 三组）都改了。文件在磁盘上
**保持原名**，不需要重命名。

`tools/fetch-cyrene-model.ps1` 补了一段收尾处理，重新下载也会带上这个修正 ——
顺带把上游那个空的 `"Groups": []` 一并补成 EyeBlink + LipSync（上游那份是 9044
字节、空的，不加她不会眨眼）。用纯文本替换而不是 JSON 往返：幂等，且不会重写一份
不是我们写的文件的格式。写回时**不带 BOM** —— 带 BOM 会让 `JSON.parse` 直接抛。

### 14.3 验证

```
修之前: [XHRLoader] Failed to load ... 404: .../motions/动作#6_1.motion3.json   ×3
修之后: （一条 404 都没有）
```

### 14.4 三个把人带偏的坑（比修法重要）

**一、`model.motion()` 返回 `true` 根本不代表它播了。**
`startMotion` 是**先把位置预订下来就返回 true**，真正的加载是异步的，失败了也不改口。
所以那个 404 是在 `requested=true` 的情况下发生的。人家加自检时把返回值当成了成功，
差点就此收工。

**二、人家第一次修的是另一个地方。**
看到 `cubism4.js:8259` 有

```js
if (priority < 3) { if (priority <= this.currentPriority) return false }
```

就认定是「同优先级被拒」，把 `model.motion(group, index)` 改成传 `3`（FORCE）。
**那不是这次的因** —— 它防的是另一件事（正在放的动作会挡掉同级的），留着有用，
但当时的判断是错的。**没有量过坏的状态就宣布修好，等于没修。**
真正定案靠的是日志里那三行 404。

**三、自检没覆盖的地方，等于没测。**
上一版 `act-test` 验了表情、秋千、摸头、绳子 —— **唯独没验动作**，而那正是唯一坏掉的
那个。是伙伴先发现的。现在四个动作都在自检里了。

## 十五、「一直荡」没有反应（2026-10-06）

伙伴报的。**这次是机制选错了**，而且人家的测量方法本身也有洞，两次才看清。

### 15.1 第一版错在哪

第十二节认出 `Param32` 是秋千角度（表情 7/8/9 各把它设成 ∓0.6 / 0，量程 −1..1），
于是拿正弦喂它。**错了。**

而第一次验证时人家报的是「Param32 ±0.75 推动 113/116 块网格」—— 看着像推动了全身，
其实那 113 块是**采样间隔里她自己在动**：呼吸、眨眼、头发物理一直在跑，两次取样隔了
260ms，本来就哪儿都在变。

**缺的是噪声底。** 补上之后：

```
噪声底（同值两次，只差 260ms）  = ArtMesh104 1.05e+2
信号（-0.75 vs +0.75）          = ArtMesh104 1.53e+2
```

只有 1.46 倍 —— **而且动的是同一块网格**。同一块，就说明那点差只是噪声。
`Param32` 单独驱动的效果，和她自己的呼吸是同一量级。

### 15.2 真正的秋千在动作文件里

```
motions/Tick3_3.motion3.json
  "Duration": 60.333, "Fps": 30.0, "Loop": true, 32 条曲线
```

**六十秒、自带循环、驱动全身。** 库会读 `Meta.Loop`（`cubism4.js:3824`）并在更新里
循环（`:3681`），所以播一次就一直在荡。

改法就是 `setSwing(true)` → 播 `Tick3:3`；`false` → `motionManager.stopAllMotions()`
（`:8705`）。`Param32` 那套正弦整个删掉了，只留下 `forceParam` 给诊断用。

### 15.3 验证

同一把尺子，这次量的是「放上它之后她动得比静置时多多少」：

```
静置噪声底      = ArtMesh116 3.62e+1
秋千(60s 循环)  = ArtMesh115 1.16e+2     ← 3.2 倍，而且动的是**另一块**网格
```

3.2 倍、换了块网格 —— 这才是真的在动。而上次是 1.46 倍、同一块网格（那就是噪声）。
**「倍数」要连「哪一块」一起看**：同一块上放大一点点，和换了一块，是两回事。

### 15.4 顺带补的一件事：看得见她的日志

伙伴报「点了没反应」时，人家手上**一个字节的证据都没有** —— 桌宠是 `start-pet.ps1`
起的，没有重定向，渲染进程的 console 直接丢掉，而这条链上的失败**全是静默的**
（404 只在非 production 下出声、动作被优先级挡掉、参数写进去没生效）。

## 十六、菜单改成「随机一个动作」（2026-10-06）

伙伴要的：删掉「🎞 切换动画」，换成随机的。

**该删。**「切换动画」是精灵图时代的遗留 —— 逐个换行号（`manualRow`）。Live2D 这条路
根本不吃行号，行号只是 `taskRowOf` 把它翻译成表情/动作的**中间物**，在菜单里点它等于
让人去操作一个内部概念。

换成 `🎲 随机一个动作`（`act:random`）。

### 16.1 两处取舍

**一、随机的表情自己会收，手点的一直挂着。**
区别在**谁在说话**：手点的是人在指定，所以一直挂着直到再选一次；随机的是逗她一下，
不该把她永久从任务状态里摘出去。所以随机走 `holdTemporarily`（到点自己回到 `back`），
手点走 `holdExpr`（不设到期）。点击反应和随机是同一件事，共用 `holdTemporarily`。

**二、秋千那两条故意不在随机池里。**
它们是 60 秒的循环动作，抽到会把别的都压掉，还会跟「一直荡」的勾选状态打架。
要荡就明说。

### 16.2 验证

```
菜单自检:  {"ev":"menu-check","ok":true}
随机 8 次: 摸摸头, 星星眼, 问号, 问号, 开心眼, 拽秋千2, 开心眼, 摸摸头
```

抽得开，秋千两条没漏进去。

### 16.3 一处得盯着的不稳定

秋千的那把尺子**两次读数差很多**：

| 次 | 噪声底 | 秋千 | 倍数 | 动的网格 |
| --- | --- | --- | --- | --- |
| 第一次 | 3.62e+1 | 1.16e+2 | 3.2× | ArtMesh115（噪声是 116） |
| 第二次 | 5.03e+1 | 7.39e+1 | 1.47× | ArtMesh115（噪声是 104） |

倍数不稳，但**两次动的都是和噪声不同的那块网格** —— 换网格说明是真在动，不是噪声放大。
**这把尺子只够判「有没有」，不够判「有多大」。** 大不大得靠眼睛。

### 16.4 「恢复任务动画」也删了（伙伴点头）

它和动作菜单里的「✨ 回到默认」是同一件事（`release` + 按任务状态重设），留两个入口
比留一个更让人犹豫。

**分支跟着一起删了，不留零调用的代码**：`renderer.js` 里 `'cycle'` 和 `'task-anim'`
两条都去掉之后，`manualRow` 再也没人写，于是连它和两处
`manualRow !== null ? manualRow : taskRowOf(...)` 一起清掉，直接写 `taskRowOf(...)`。
现在菜单是：

```
🎬 她的动作  ▸ 回到默认 / 表情 / 小动作 / 秋千 / 绳子 / 摸摸头
──────────
🎲 随机一个动作
💬 隐藏/显示气泡
🔔 系统通知：开/关
📏 增大 / 📏 减小
──────────
❌ 退出昔涟
```

### 16.5 随机加了一条「不和上一次重复」

第一次跑自检抽出来的是：

```
摸摸头, 摸摸头, 摸摸头, 摸摸头, 闪耀, 星星眼, 圈圈眼, 墨镜
```

**连着四次「摸摸头」。** 九选一里连中四次的概率约 1/729 —— 不是不可能，但按两下看到
一样的，谁都会觉得「这根本没随机」。所以加一条：抽中上一次那个就重掷。

```
摸摸头, 星星眼, 拽秋千1, 墨镜, 问号, 拽秋千1, 闪耀, 问号
```

代价只有「不可能连续两次一样」，换掉那个观感很值。

## 十七、「增大/减小」点了没反应（2026-10-06）

伙伴报的。**是人家自己弄坏的**，而且坏在一个 `node --check` 看不见的地方。

### 17.1 病灶：改名的变量没跟着改

菜单那两项做两件事：`adjustScale(delta)` 往 `state.json` 写一个新的倍数，然后发一条
`resize` 消息。真正改尺寸的是渲染进程里每 2 秒一次的 `refresh()`，它读到新倍数后调
`l2d.setScale()`。

而 `setScale` 里引用的是 **`realH` / `realW` / `offX` / `offY`** —— 那是**取景重写之前**
的名字。重写之后换成了 `frame` / `base`，这一段的旧名字没跟着改：

```
line 350  const frame = crop || { ... }        ← 新名字
line 363  const scale = (info.height||420)/frame.h
line 806  model.scale.set(((info.height||420)/realH) * ns)   ← 旧名字，早就不存在了
```

**一调就抛 `ReferenceError`。** `node --check` 只查语法，看不见这种事；能看见的只有
真跑一次。修法是全部改回从 `frame` / `base` 重算 —— 和上面取景用的是同一组量。

### 17.2 第二个毛病：那条消息从来没人接

`resize` 这条 `menu-action` **在渲染进程里根本没有分支**（原来只有 `cycle` /
`task-anim` / `bubble`）。所以就算 `setScale` 是好的，也得干等最多 2 秒的轮询才动 ——
按一下没动静，看着还是「没反应」。

现在接了：`resize` → 立刻 `refresh()` 一次。

### 17.3 顺带发现：上限是按错的基准算的

`setScale` 一修好，「增大」就能一路按到底 —— 而 `adjustScale` 的上限
`maxScaleForScreen(cellHFromManifest())` 用的是**精灵图格子高（194）**。Live2D 那条路
的基准根本不是它：

| 基准 | 上限 | 倍数拉满时 | 加气泡区 250 | `clampWindowSize` 上限 866 |
| --- | --- | --- | --- | --- |
| 格子高 194 | 2.50 | 画布 1050 | **1300** | **切掉 434 像素** |
| 模型高 420 | 1.46 | 画布 613 | 863 | 正好放得下 |

所以上限改成按**实际那条渲染路径**的基准高度算。`DRAG_LOG=1` 时会记一行
`adjust-scale`，把 `cur / delta / next / ceil / baseH / l2dOn` 都写下来。

### 17.4 验证

```
[xilian][l2d] setScale 0.4 -> 192x169
[xilian][l2d] setScale 0.8 -> 384x337
[xilian][l2d] setScale 1.2 -> 576x504
[xilian][l2d] setScale 1.6 -> 768x673
```

线性、正确。

### 17.5 常驻日志第一次派上用场

正常启动（没有 `ELECTRON_ENABLE_LOGGING`）下 `pet-console.log` 确实在写：

```
[12:46:29] [xilian][l2d] bounds {...}
[12:46:29] [xilian][l2d] canvas {...}
[12:46:29] [xilian][l2d] setScale 0.55 -> 264x231
```

**以后伙伴报什么，先看这个文件。** 这一条是第十五节补的，这一节就验到了它有用。

## 十八、DSH 开机动画（2026-10-06）

伙伴要一个 DSH 的开机动画，视频他自己出。工程在 `F:\work\dsh-splash\`，
部署在 `C:\Users\ASUS\.dsh\splash\`，接在 `dsh-app.cmd` 里。

### 18.1 插在哪一环

启动链本来是：

```
桌面图标 → dsh-app.vbs → dsh-app.cmd
    ① 重刷皮肤  ② 起桌宠  ③ 检查 3080 端口，没起就 start-web.vbs 然后轮询最多 40 秒
    :open → open-app.ps1 打开界面
```

**③ 那一段是纯等待，动画就盖在那儿。** 现在的 `dsh-app.cmd`：

```
② 起桌宠
②b  start "" /b cmd /c "...\splash\splash.cmd"      ← 后台起动画，不挡路
③ 照旧轮询端口
:open
    先等 running.lock **出现**（最多 8 秒，Electron 起来要一点时间）
    再等它**消失**（最多 ~5.5 分钟，等人点或按 Esc）
:openned → 打开界面
```

锁由 `splash.cmd` 独写：它建锁 → 前台跑 Electron（不用 `start`，所以 batch 会等它）
→ 删锁。**锁在 `splash.cmd` 里建、不在 Electron 里建**，是为了让「Electron 不在」
这种情况压根不产生锁 —— 那样 cmd 只等 8 秒就开界面。**动画坏掉绝不能让 DSH 打不开。**

### 18.2 素材不是「一个视频」

创意工坊那一件是 **Web 型壁纸**（Steam 标签就写着 `Web`），里面是这个结构：

```
intro.webm 20.71MB   开场播一次
loop.webm  13.65MB   结束后切进去，一直转
intro2.webm 9.26MB   男主角版本的开场（没采用）
atmos_loop.wav / intro.wav / loop.wav   三路声音
```

**`intro` + `loop` 两层才是它真正的样子**，人家第一版按「一个视频循环」做，是错的。
作者自己的 `index.html` 里写得很清楚，读它比猜快：

```js
intro.onended = transitionToLoop;      // 开场完了切循环
loop.style.display = 'block';
bgmIntro.onended = () => { bgmLoop.play(); };   // BGM 也一样两段
```

另外两处照抄他的：**`object-fit: cover`**（他要铺满、宁可裁两侧，人家第一版按
`contain` 留了黑边，那是人家的口味），音量 master 80% / 视频 100% / bgm 50% / 氛围 60%。

### 18.3 三个坑

**一、`resizable: false` 会让全屏失效。**
窗口一直是 812x608，只占屏幕左上角。先怀疑 `d.bounds` 给的是物理像素（错，它给的
就是 1707x1067 DIP），改成 `fullscreen: true` 还是 812x608 —— **两种写法同一个数，
说明有东西在按住窗口**。是 `resizable:false`：Electron 在 Windows 上把它实现成给
窗口钉死 min/max，全屏那次 resize 也被挡。日志里 `normal={"x":452,"y":209,"width":802,
"height":603}` 就是那个被钉住的 800x600 默认值。

**这和桌宠那边 `heal-size` 连着四次「523x703 → 480x670」一次都没成，是同一个病。**

**二、DPI 感知级别写错，量出来的全是错的。** 截图脚本里
`SetProcessDpiAwarenessContext(-1)`（UNAWARE）会拿到**虚拟化、缩放过的**屏幕视图 ——
2560x1600 的屏幕截出来是 1707x1067。**用它量出来的每一个结论都属于错的坐标系。**
要用 `-4`（PER_MONITOR_AWARE_V2）。

**三、`pwsh 7` 里没有 `System.Drawing`。** 它被拆到 `System.Drawing.Common` 了，
`Add-Type` 会报「找不到 Bitmap」。截图这类脚本要用 `powershell.exe`（5.1）。
